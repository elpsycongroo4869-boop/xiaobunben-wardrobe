# 衣橱 2.5｜世界、职业、摄影随机引擎与质量保证

## 根本缺陷及修复

V1.1的「构思3个候选→评审选最美」是**偏好排序，不是随机**。LLM容易偏向高概率的词，例如星图、绘图师、飞艇、魔法图书馆、哥特蕾丝。解决方案是：**先用模型外部随机源锁定大类/职业，再让模型负责美术细化，不得以审美替换抽签结果。**

## 随机算法

参照 `scripts/roll_wardrobe.py`。v2.4 首先按独立概率随机选择三路线（职业70%、纯Cos20%、融合10%）；职业与融合才进入原16类袋，纯Cos不占类别名额；三路线都占摄影包成功名额；纯Cos和融合各自有24位Cos角色无放回袋。细节见 `references/cosplay-engine.md`。

原职业路线规则：

1. 读取 `category-pool.json` 的16个非重叠大类，每类8个职业种子。每次成功出图进入一次「乱序袋」记录。一个16张的完整轮次中，每一类恰好出现一次（顺序用 `secrets.SystemRandom` 真随机决定）。这是**无放回、动态均匀抽取剩余项**；不能误称每次16类独立等概率。
2. 为避免跨轮边界撞类，若允许，则剔除成功历史中的最近3类；如果会让本轮无可选类，则恢复剩余候选，优先完成乱序袋。
3. 选定大类后，20%（每次独立）进入原创职业入口，80%从8个职业等机会抽取（过滤最近10张同职业后抽取）。原创职业的**大类与行动/对象/情境**仍由程序抽签；模型只负责推导世界观中确实需要这种工作的岗位，而不是随手取个好听名字。
4. **摄影包**从24类乱序袋中选择，与世界乱序袋独立。再从14个镜头构图、12个故事瞬间独立抽选，并从轻/中/重按30%/50%/20%抽取风格强度。摄影包详见 `camera-packs.json`；视觉执行与验收详见 `photography-engine.md`。场景仍在大类相关地点中随机提供建议。
5. 最近6张显著母题（蒸汽飞艇、星图绘画、哥特卧室、机械风等）做语义去重。如果模型新构思碰撞，需要重新构造场景/动作或在必要时重新抽职业，但不允许只因为喜欢某一套衣服而重抽。
6. 前8张成功的 V2 默认图，特别回避重复频繁的「绘图/星图/飞艇」类职业名称作为过渡冷却；第9张起恢复普通抽取。

## 回合统计的注意事项

世界轮次计数统计 `mode=random, status=success, version in (2.0,2.1,2.2,2.3,2.4,2.5)` 且 `lane` 为 career/fusion（旧版缺失 lane 视为 career）的历史行；摄影包24类乱序袋仅统计包含 `camera_pack_id` 的成功随机行。指定主题、挑战模式、抽中但未生成、被图像系统拒绝的方案，都不占默认随机模式的16类名额。

如果历史丢失、无法写入，乱序袋只能在本次可见范围内运作；**不要伪称跨会话严格保证不重复**。历史的保存属于持久化系统，不属于语言模型会自动完成的动作。

## 大类抽签与职业的公平性

每一大类**每16张随机成功作品出现1次**，避免现实职业因细分数量多而大幅压过奇幻类或科幻类。抽选后才细化身份，审美偏好不影响概率。

128个预设职业种子是**启动池，不是世界观上限**。职业创新不仅新名字，更要包含：职责（谁需要它）、行动（具体怎么做）、工具（视觉可识别）、服装（符合工作和文化）、风险/任务（这张照片讲什么）。如只是把「星图绘图师」改名成「星云地图师」，判定为相同职业母题，应重新创造，而非视为新职业。

## 历史最小字段

日期、模式、版本、成功状态、世界大类ID、职业名、地点、摄影包ID、镜头形式、摄影强度、故事瞬间、视觉母题、draw_id。近10个职业、近3个类别、近6个视觉母题都应在创作时检查。相同职业的**同义变体也算重复**，不只比较字符串。

### 人工可操作流程

```bash
# 可执行 Python 的环境：真正随机，保存待生成方案
python3 scripts/roll_wardrobe.py --history references/history.jsonl --output /tmp/wardrobe-draw.json

# 用图片生成器成功产出照片后，执行登记；失败不要执行
python3 scripts/roll_wardrobe.py --history references/history.jsonl --commit /tmp/wardrobe-draw.json --audit-file /tmp/audit.json --motif 'field-research'

# 原创职业出图成功，要登记实际创造的名字
python3 scripts/roll_wardrobe.py --history references/history.jsonl --commit /tmp/wardrobe-draw.json --audit-file /tmp/audit.json --role '新职业实称'
```

### 没有 Python / 没有可写历史时

- 若存在合规的随机数工具，可将16个大类编号1–16，根据尚未用过的大类建立剩余表，再抽 1–N；再分别抽原创概率、职业索引、摄影包、镜头和瞬间。记录实际掷骰来源和抽选结果。
- 如果缺乏任何真正随机的工具，只能执行「可见历史去重 + 轮换大类 + 职业细化」；**这叫模拟随机或尽力多样化，不是概率正确的真随机**。应向用户简单说明区别，不许捏造随机种子、抽签或自动历史。
- Skill 安装 ZIP 内的历史文件不是联网数据库；读写受限时把历史导出到用户可访问的单独文件并重新提供，不得写入失败却说已经更新。

## 验收口径

- 连续成功生成16次，日志中的16个大类无重复；第二轮重新抽签。
- 连续成功生成24次，日志中的24个摄影包无重复；第二轮重新抽签。
- 检查图像内容与摄影包实际吻合，不能因生成了一张漂亮的居家自拍而忽略职业。
- 连续成功生成10次，原则上无重复具体职业（不可行时须记录放宽原因）。
- 1000+次仿真下原创职业事件占比应接近20%（统计波动自然存在）。
- 无论用户是否曾喜欢黑丝袜/哥特裙，默认大类选取过程不使用此偏好作为随机权重。
- 图像生成被拒绝，不增加成功次数；历史记录只有实际保存才算生效。


## 2.2 历史兼容

旧版 2.0、2.1 的已成功随机照片仍参与世界类别乱序袋；v2.2 新的成功条目继续摄影风格乱序袋。v2.2 保存 `--commit` 必须提交真实图片人工验收 JSON（`--audit-file`），失败图片不计数。

## v2.3 成功提交补充

成功照片经过人工逐项验收，审核 JSON 还需 `image_file`（真实可访问图片绝对路径）与 `image_sha256`（文件计算值）；脚本核对图片文件存在、格式标识与摘要，但不能自动识别画面身份/场景。2.2 尚未成功的抽签可复用；不会生成新抽签 ID。失败日志单独写，不影响成功乱序袋。

## v2.4 三路线与服装模式

- 70%纯职业 / 20%纯Cos / 10%职业×Cos融合。原16世界袋仅由职业/融合的成功照片消耗；原24摄影包袋三条路线共用。
- 纯Cos和融合各自使用24位角色独立无放回袋，成功才消耗名额；指定模式不参与。
- 服装演绎独立抽签 10%现实功能、20%轻女性化、55%游戏女性化、15%幻想强化。黑丝袜无默认出图提示词，完全不参与抽签与验收。
- 旧 v2.2/2.3 已锁定抽签仍可用 `prepare_shoot.py` 重新编译，默认职业路线。

## v2.5 历史兼容

抽签成功历史支持 2.0—2.5；之前的未成功 v2.4 抽签保持独立 pending，**不参与成功乱序袋**。摄影包与职业概率不变；交接器只做内容一致性校验，绝不增加抽签次数。
